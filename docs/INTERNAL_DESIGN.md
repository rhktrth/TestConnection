# TestConnection 内部設計

この文書は、[`EXTERNAL_DESIGN.md`](EXTERNAL_DESIGN.md) で定めた外部仕様を実現するために維持する内部構成、各部の責務、処理順序、並行処理、リソースの所有関係、エラー処理を定義します。

利用者、接続相手、OS、設定ファイル、結果出力から観測できる事項は外部設計を正本とし、この文書へ同じ内容を重複記載しません。

## 1. 設計方針

### INT-BOUNDARY-001: 要件・外部仕様を実装都合で変更しない

内部構造は `REQUIREMENTS.md` と `EXTERNAL_DESIGN.md` を満たすために決めます。実装しやすいという理由だけで上位仕様を暗黙に変更してはいけません。

### INT-SIMPLE-001: 変更理由が同じものだけを共通化する

単にコードが似ているだけでは共通化しません。同じ仕様、同じライフサイクル、同じリソース所有関係によって一緒に変更されるものだけを共通化します。将来拡張だけを目的としたサービス層、DI フレームワーク、登録機構などは追加しません。

## 2. 各部の責務

### INT-UI-001: MainForm

`MainForm` は WinForms の画面表示とアプリケーション全体の操作受付を担当します。

- 試験定義の追加・削除
- `TestSession` への開始・停止指示
- 結果表示、ファイル出力、統計表示、効果音
- 結果ログ出力先とログファイル名の利用者設定への読込み・保存
- 有限回数の自然完了通知を UI スレッドへ引き渡し、実行時リソースを終了して待機状態へ戻すこと
- NIC の一時設定・復元の画面操作
- バックグラウンド処理からの通知を UI スレッドへ引き渡すこと

CSV の解析、入力検証、通信処理を UI のイベント処理へ直接埋め込みません。

### INT-CFG-001: 設定

`TesterDefinition` は役割、ローカル側・接続先、プロトコル、ポート番号を表す内部データです。

- `TesterDefinitionFile` は `EXT-CFG-002` の CSV 読込み・保存と、行番号付きの形式エラー生成を担当する。読込み時は既存互換のため 6 列目以降を無視し、保存時は常に 5 列とする。
- `TesterDefinitionValidator` は `EXT-CFG-001` の入力検証を担当し、ローカル IP と DNS サーバーを IPv4 に限定し、Ping 以外のポートを 1 から 65535 に限定する。
- `ResultLogSettings` は結果ログの出力先を既存の利用者設定値へ対応付ける。
- 同じ設定値を各試験処理で別々に重複保持しない。

### INT-SESSION-001: TestSession

`TestSession` は一回の試験実行における試験処理の生成と、クライアント・サーバーの開始・停止を調整します。

- 試験定義を検証し、`TesterFactory` で具体的な試験処理を生成する。
- 結果通知などのコールバックを接続する。
- `EXT-RUN-001` に従い、サーバーの待受準備が完了または失敗したことを確認してからクライアント処理を開始する。
- 手動停止時はクライアント処理を終了してからサーバー群を停止する。
- 有限回数のクライアント反復が自然完了した場合は、サーバー群を停止してセッションを終了し、完了通知を一度だけ上位へ返す。
- 二重開始・二重停止を防止する。

### INT-RUNNER-001: ClientTestRunner

`ClientTestRunner` は一つのバックグラウンド処理で、クライアント試験を登録順に実行します。

- 有限回の反復は指定回数で終了する。
- repeat count が 0 の場合は停止要求まで反復する。
- 試行間の待機は停止要求で解除できるようにする。
- 停止時は現在実行中の試験処理の `Cancel()` を呼び、バックグラウンド処理が終了するまで待つ。
- クライアントが存在する有限回の反復が停止要求なしで完了した場合だけ、自然完了コールバックを呼ぶ。手動停止やクライアント 0 件では自然完了として扱わない。

### INT-SERVER-001: TesterServer

`TesterServer` はサーバースレッド、起動時の同期、停止順序を共通管理します。

- `Start()` は listener / socket の初期化結果が確定するまで呼出元を待たせる。
- プロトコル固有の待受処理は具体的なサーバークラスが担当する。
- 停止時は listener / socket を閉じて待受を解除し、スレッド終了を待つ。
- 停止のための close を通信失敗として数えない。

### INT-TESTER-001: 試験処理の共通構造

`TesterBase` は試験定義、タイムアウト、成功・失敗件数、結果の共通書式と通知を保持します。

`TesterClient` は一回の試行を `RunOnce()` として実行し、`Cancel()` で現在の待ち状態を解除します。停止要求による中断は通常の通信失敗と区別します。

`TesterFactory` は検証済みの試験定義から TCP / UDP / DNS / Ping の具体的な試験処理を単純な分岐で生成します。

### INT-RESOLVE-001: RemoteEndpointResolver

TCP / UDP / Ping クライアントの名前解決と IPv4 アドレス選択規則を `RemoteEndpointResolver` に集約します。

- `EXT-RESOLVE-001` の規則を一か所で実現する。
- 名前解決は各試行の直前に行う。
- DNS クライアントはこの処理を使用しない。

### INT-NIC-001: NicConfigurationService

`NicConfigurationService` は Windows NIC の現在状態取得、設定、復元を担当します。

- `EXT-NIC-*` を実現するため、NIC ごとに変更前の状態を保持する。
- UI から受け付けるサブネットマスクとデフォルトゲートウェイは IPv4 に限定する。
- TestConnection が変更しない DNS 設定などまで管理対象を広げない。
- UI 側には WMI 操作の詳細を持たせない。

## 3. プロトコルごとの実装範囲

| 外部仕様 | 主な実装 | 内部責務 |
| --- | --- | --- |
| `EXT-TCP-001` | `TcpTesterClient` | ローカルアドレス指定、名前解決、接続、タイムアウト・停止、後始末 |
| `EXT-TCP-002` | `TcpTesterServer` | 待受、接続受付、受付後の接続の後始末 |
| `EXT-UDP-001` | `UdpTesterClient` | ローカルアドレス指定、名前解決、データグラム送信、後始末 |
| `EXT-UDP-002` | `UdpTesterServer` | データグラム受信、停止時の受信待ち解除 |
| `EXT-DNS-001` | `DnsTesterClient` | 固定問い合わせ送信、応答待ち、タイムアウト・停止、後始末 |
| `EXT-PING-001` | `PingTesterClient`, `IcmpEchoPacket` | raw ICMP の送受信と Echo Request / Reply の対応確認 |

各プロトコル固有クラスは、その外部仕様に必要な通信だけを担当し、アプリケーション層のプロトコル処理まで責務を広げません。

## 4. 起動・停止順序

開始時は次の順序とします。

1. 試験定義を検証して試験処理を生成する。
2. サーバーを登録順に `Start()` し、待受準備の成功・失敗を確定する。
3. クライアントの反復処理を開始する。

手動停止時は次の順序とします。

1. クライアントの反復処理へ停止を要求する。
2. 現在実行中のクライアントの `Cancel()` で待ち状態を解除する。
3. クライアント側のバックグラウンド処理終了を待つ。
4. サーバーを停止し、待受状態を解除する。
5. サーバースレッドの終了を待つ。

有限回数の自然完了時は、クライアント側のバックグラウンド処理が終了状態へ遷移した後、`TestSession` がサーバー群を停止し、最後に UI へ完了を通知します。サーバーのみの実行ではこの自然完了経路を使用しません。

`Thread.Abort()` は使用しません。

## 5. リソースのライフサイクル

TCP / UDP / DNS / Ping クライアントは、正常終了、エラー、タイムアウト、停止要求の各経路を共通の後始末へ収束させます。ソケットなどの所有者を曖昧にしません。

停止のために閉じたソケットなどが発生させる例外は、成功・失敗件数へ反映しません。

## 6. 結果の組み立て

`TesterBase` は `EXT-RESULT-001` で定めた共通部分を組み立てます。各プロトコル固有クラスは、そのプロトコルに必要なメッセージだけを生成し、共通書式を重複実装しません。

結果ログの出力先は `ResultLogSettings` で利用者設定の三つの boolean 値と一意に対応付け、UI はその対応を用いて読込み・保存します。ログファイル名は既存の `logfilename` 利用者設定を使用します。

内部設計を変更するときは、最初に `REQUIREMENTS.md` と `EXTERNAL_DESIGN.md` が変更不要かを確認します。必要な場合は上位文書から順に改訂し、内部設計を確定してからソースコードを変更します。
