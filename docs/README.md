# TestConnection ドキュメント構成

このディレクトリの文書は、TestConnection を仕様駆動で変更するための現在有効な正本です。

TestConnection の仕様駆動開発では、一般的なソフトウェア設計の流れに沿って、**要件 → 外部設計 → 内部設計 → 実装 → テスト** の順序を必ず守ります。

## 1. 正本と役割

| 段階 | 正本 | 定義する内容 |
| --- | --- | --- |
| 要件 | [`REQUIREMENTS.md`](REQUIREMENTS.md) | 何を満たす必要があるか。目的、機能要件、非機能要件、制約 |
| 外部設計 | [`EXTERNAL_DESIGN.md`](EXTERNAL_DESIGN.md) | 利用者、接続相手、OS、ファイル、出力から観測できる仕様、`EXT-*`、`AC-*` |
| 内部設計 | [`INTERNAL_DESIGN.md`](INTERNAL_DESIGN.md) | 各部の責務、処理順序、ライフサイクル、並行処理、リソースの所有関係、`INT-*` |
| 実装 | `src/`、プロジェクトファイル、必要な設定 | 内部設計を具体化する本体実装 |
| テスト | `tests/` | 実装が要件・外部設計・内部設計を満たすことの検証 |
| 運用 | [`OPERATIONS.md`](OPERATIONS.md) | ビルド、テスト、配布物作成、CI、リリースの手順 |
| 設計判断 | [`adr/`](adr/) | 重要な設計判断の理由と見直し条件 |
| 利用者向け | [`../README.md`](../README.md) | 概要、導入、基本的な使い方、重要な注意事項 |

`AGENTS.md` は、この工程と正本を維持するための作業規則です。製品仕様そのものの正本にはしません。

## 2. 必須の開発順序

機能、外部挙動、内部構造を変更する場合は、次の順序で進めます。後段を先に変更し、前段を後付けしてはいけません。

1. **要件**
   - 依頼が既存要件の範囲内か、要件そのものを変更するものかを判断する。
   - 要件変更であれば、最初に `REQUIREMENTS.md` を更新し、`REQ-*` を確定する。
2. **外部設計**
   - 確定した要件を、外部から観測できる仕様へ具体化する。
   - `EXTERNAL_DESIGN.md` の `EXT-*` と必要な `AC-*` を確定する。
3. **内部設計**
   - 外部仕様を実現するための責務、処理順序、状態、並行処理、リソースの所有関係、エラー処理を決める。
   - `INTERNAL_DESIGN.md` と必要な `INT-*` を確定する。
4. **実装**
   - 確定した内部設計を、ソースコード、プロジェクトファイル、設定などへ実装する。
   - 実装上の都合で上位設計を黙って変更しない。変更が必要なら、該当する上位段階へ戻って先に修正する。
5. **テスト**
   - 実装が `REQ-*` / `EXT-*` / `INT-*` / `AC-*` を満たすことを検証する。
   - 不足する回帰テスト・受入テストがあれば追加または更新する。
6. **横断的な整合性確認**
   - 要件、外部設計、内部設計、実装、テスト、README、OPERATIONS、ADR に矛盾や不要な重複がないことを確認する。

この順序は、工程ごとにコミットを分けることを意味しません。同じ PR や同じコミットに含めても構いませんが、**判断と編集は必ず上流から下流へ進めます**。

## 3. 変更分類

着手時に変更を次のいずれかへ分類します。

- **A: 要件変更** — 目的、提供機能、制約、非機能要件が変わる。
- **B: 外部設計変更** — 要件は同じだが、外部から観測できる仕様が変わる。
- **C: 内部設計変更** — 外部仕様は同じだが、内部の責務や処理方式が変わる。
- **D: 実装のみ** — 要件・外部設計・内部設計を変えずに、不具合修正や整理を行う。
- **E: 運用のみ** — ビルド、テスト、配布物作成、CI、リリースの手順だけが変わる。

A の場合は B / C / 実装 / テストへの影響を、B の場合は C / 実装 / テストへの影響を、C の場合は実装 / テストへの影響を必ず確認します。

D の場合でも、実装を変更する前に、既存の `REQUIREMENTS.md`、`EXTERNAL_DESIGN.md`、`INTERNAL_DESIGN.md` が変更後も正しいことを確認します。

## 4. 仕様 ID と未確定事項

- 要件: `REQ-<AREA>-NNN`
- 外部仕様: `EXT-<AREA>-NNN`
- 受入条件: `AC-<AREA>-NNN`
- 内部設計: `INT-<AREA>-NNN`
- 未確定事項: `TBD-<AREA>-NNN`

ID は章立ての代わりではありません。変更、レビュー、対応関係の確認に価値がある単位だけに付与します。

未確定事項は `TBD-*` として上流文書で明示し、ソースコード、現在のテスト、一般的なベストプラクティス、AI の推測だけで確定してはいけません。

## 5. 追跡可能性

原則として、次の対応を追跡できる状態を維持します。

```text
REQ -> EXT / AC -> INT -> 実装 -> テスト
```

逆方向にも、テストやソースコードから、どの内部設計、外部仕様、要件を実現・検証しているか説明できることを目標とします。

対応関係を示すためだけの巨大な独立台帳は作らず、`REQUIREMENTS.md`、`EXTERNAL_DESIGN.md`、`INTERNAL_DESIGN.md` の対応表を利用します。

## 6. 文書の重複を避ける規則

- REQUIREMENTS は「何を必要とするか」を書き、具体的な画面動作、通信方式、クラス設計は書かない。
- EXTERNAL_DESIGN は外部から観測できる仕様を書き、C# のクラスや非公開実装は書かない。
- INTERNAL_DESIGN は内部の責務・方式を書き、外部仕様を詳細にコピーしない。
- README は利用者向け説明に限定し、詳細は外部設計を参照する。
- OPERATIONS は実際のコマンド、CI、リリース操作に限定する。
- ADR は仕様一覧ではなく、重要な判断理由と見直し条件に限定する。
- テストは同じ仕様を複数階層で重複して固定しない。

重複排除の目的は文書数を減らすことではありません。**要件・外部設計・内部設計を明確に分離し、それぞれの正本を一つにすること**を優先します。

## 7. 矛盾が見つかった場合

矛盾をソースコードに合わせて文書だけ修正してはいけません。

1. `REQUIREMENTS.md` で現在の要求を確認する。
2. 外部から見える仕様の問題であれば `EXTERNAL_DESIGN.md` を確認する。
3. 内部方式の問題であれば `INTERNAL_DESIGN.md` を確認する。
4. 上流から正しい内容を確定する。
5. その順序で実装を合わせる。
6. 最後にテストで検証する。

下流の現在状態から上流仕様を後付けするのではなく、常に上流から下流へ整合させます。
